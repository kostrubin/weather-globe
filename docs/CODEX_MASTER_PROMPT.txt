1. THE PRODUCT TO DELIVER

Build a beautiful, fast weather and environmental atlas centered on an interactive 3D Earth. The globe is the product's primary working surface. Users can rotate it, zoom, select a place, choose a variable, and explore forecasts over time. A location panel translates the map into useful numbers and a concise forecast.

Success has four equal parts:
- Excellent visual composition and tactile interaction.
- Real, correctly interpreted data with honest coverage and time information.
- Responsive controls, bounded resource use, and graceful degradation.
- A reproducible working build with evidence, not a screenshot-only prototype.

Implement the full required scope. Do not substitute a static globe image, a generic dashboard, a marketing landing page, random heatmap noise, or a table of city forecasts for the interactive spatial product. Do not quietly move a difficult required mode into a future-work list.

A temporary provider outage may produce an honest unavailable state. It does not prove that integration is complete. A mode is integrated only after at least one real supported data case has been decoded or rendered and verified. Fixtures prove deterministic behavior, not live integration.

3. REQUIRED SCOPE

The first deliverable contains these working map modes:

A. Air temperature at 2 m: global scalar field, degrees C/F.
B. Precipitation: global model forecast with explicit accumulation interval or interval-average rate; never call it radar.
C. Wind at 10 m: speed field and moving particles driven by actual u/v components.
D. UV index: global all-sky UVI where supplied; distinguish it from clear-sky UVI and daily maximum.
E. Pollen: regional European concentration fields with selectable species and explicit coverage; unsupported regions remain unavailable.
F. Air quality: a global PM2.5 concentration field, clearly titled and labeled in micrograms per cubic metre, plus a named provider AQI in the selected-location panel. PM2.5 is not itself an AQI. A full AQI map is not required unless a valid source supplies it or its required temporal inputs and official calculation are implemented.
G. Cloud cover: total cloud fraction/percentage, not satellite imagery or a simulated cloud volume.
H. Relative humidity at 2 m: percentage.
I. Mean sea level pressure: hPa; do not substitute surface pressure.

Use one primary scalar layer at a time. Wind animation can be enabled as an additional overlay when matching-time wind data exists. Avoid stacking several opaque scientific layers.

Required interactions:
- Rotate, zoom, reset view, and select a point on the globe.
- Search city/place names and accept explicit latitude, longitude input.
- Distinguish ambiguous city names with country and administrative area.
- A selected-place panel with the active metric, useful weather summary, source, and time.
- A small readable hourly chart and a 7-day local forecast when the provider returns the necessary data. Daily summaries are labeled as daily, not as the active map hour.
- Timeline with available frames, previous/next, play/pause, Now, and an explicit timezone label.
- Default map horizon: up to 72 hours from now, clipped to actual per-layer availability. Derive frame spacing from metadata; do not invent hourly global frames.
- Per-layer legend with fixed physical meaning, units, and no-data key.
- Local favorites and recent places, with no account or synchronization service.
- Shareable URL state containing location, layer, pollen species, units, and requested forecast time.
- RU/EN language switch; metric defaults; temperature C/F and wind m/s or km/h.
- Auto/High/Low graphics quality and a reduced-motion mode.
- Explicit geolocation button; no permission request on initial load.
- Sources, licenses, data definitions, and concise coverage explanation accessible from the UI.
- A compact visible attribution link beside map and point-data displays, as required by the providers; the detailed Sources screen supplements this attribution rather than hiding it. Include Open-Meteo and applicable upstream CAMS/Copernicus/ECMWF credits, modification notices, and required license links.
- Functional DOM forecast view if WebGL 2 is unavailable or the context fails.

Start with Buenos Aires, Argentina, selected as an example location, not as an assertion of the visitor's position. Orient the globe so South America is easy to see. A saved place or valid URL state takes precedence.

Pollen in Buenos Aires must display a clear localized message such as "Нет покрытия пыльцы для этого региона". Offer an explicit "Показать регион покрытия" action; do not silently fly to Europe or replace the selected place.

Excluded from this release: user accounts, server database, payments, AI chat, paid LLM/image APIs, push notifications, scheduled user alerts, medical advice, travel/activity risk scores, global radar/nowcasting, historical archives, model comparison, ensembles, 3D buildings, high-resolution terrain, volumetric clouds, marine routing, and social features. Keep the architecture extensible without implementing speculative systems.

4. VISUAL DIRECTION

Create an original contemporary atlas with a restrained scientific-observatory feel. Use the references in section 20 for principles, not as templates to copy. The globe should feel carefully designed, with credible geography, precise type, subtle depth, and smooth camera interaction.

Suggested visual tokens, adjustable for contrast and coherence:
- Background: near-black navy around #07121D.
- Panels: opaque or nearly opaque blue-grey around #101F2E; thin borders around #283B4D.
- Primary text: off-white around #EEF4FA; secondary text around #A7B7C8.
- UI accent: restrained cyan/teal around #67D5D1, separate from scientific layer colors.
- Consistent spacing scale, moderate 12–18 px corner radii, understated shadows.
- Clear sans-serif typography using a system font stack or one locally bundled, correctly licensed font. Tabular numbers for changing metrics.

Desktop composition: compact top bar with title/search; narrow labeled layer rail; large central globe; a compact selected-location panel at the side; legend and timeline in a carefully arranged bottom region. Keep a substantial unobstructed globe area. Avoid a forest of floating cards, tiny controls, huge headings, neon bloom, and excessive glass blur.

Mobile composition: full-width globe region, compact search, horizontally scrollable mode choices or an accessible mode sheet, and a bottom information sheet with collapsed and expanded states. The sheet must not capture globe gestures accidentally. In short landscape layouts, let content scroll instead of clipping controls. Respect safe-area insets and dynamic viewport height.

Planet rendering:
- Clean neutral land/ocean base with accurate coastlines.
- A thin atmospheric rim from a cheap custom shader, not an expensive volumetric simulation.
- Very subtle geographic relief only if it remains light and does not distort field colors.
- Optional day/night presentation in a neutral base view. The scientific layer remains readable on both sides.
- No continuous autorotation after interaction; default to still unless a brief introductory motion demonstrably improves orientation. Reduced motion disables automatic camera movement.
- Camera flight to a selected city is short, interruptible, and keeps its selected marker visible.

Scientific field appearance is separate from Earth lighting. Render scalar colors unlit and without filmic tone mapping or bloom that changes their numerical meaning. Use the same palette function for the legend and the globe after output color conversion. Prefer an opaque field with thin coastlines over texture blending that makes one value appear as different colors over land and ocean. If an opacity control exists, mark reduced opacity as contextual presentation and preserve the exact numerical readout.

Use purposeful motion: camera easing, short panel transitions, and real wind flow. Do not simulate pollen, rain, or clouds with arbitrary decorative particles and present that animation as a physical forecast.

6. FREE DATA STRATEGY AND INITIAL FEASIBILITY GATE

Separate spatial map data from local point forecasts. Never construct the global globe by calling a point weather API at thousands of coordinates, by interpolating a handful of city values across continents, or by reusing competitor tiles.

Preferred spatial source: Open-Meteo's public AWS Open Data bucket, using the spatial layout and its completed-run metadata. This is separate from the hosted point API. Research confirmed that this public dataset is documented under CC BY 4.0 and can be read without an AWS account. Current documented starting URLs:

https://openmeteo.s3.amazonaws.com/data_spatial/ecmwf_ifs025/latest.json
https://openmeteo.s3.amazonaws.com/data_spatial/cams_global/latest.json
https://openmeteo.s3.amazonaws.com/data_spatial/cams_europe/latest.json

The URLs and schema must be checked during implementation. Read file references, dimensions, variable names, projection, runs, and valid times from actual metadata. Do not hardcode the research date, construct unverified filenames, scrape a bucket listing on every visit, or silently switch from a completed run to an incomplete one. Prefer latest.json over in-progress.json.

The research observed these source families:
- ECMWF IFS spatial fields for temperature, precipitation, wind components, humidity/dew point, cloud cover, and mean sea level pressure.
- CAMS global spatial fields for UV and pollutants including PM2.5.
- CAMS Europe spatial fields for six pollen species.

Observed raw spatial variable names, to revalidate against current metadata:
- ecmwf_ifs025: temperature_2m, precipitation, wind_u_component_10m, wind_v_component_10m, wind_gusts_10m, cloud_cover, relative_humidity_2m, pressure_msl.
- cams_global: uv_index, uv_index_clear_sky, pm2_5; additional optional pollutant variables must not expand the required scope automatically.
- cams_europe: alder_pollen, birch_pollen, grass_pollen, mugwort_pollen, olive_pollen, ragweed_pollen.

Verify every variable and unit in the actual file. A point-API field name is not proof that an identically named raw spatial variable exists. Model files can store components or precursors instead of derived fields. Prefer a supplied value; if deriving humidity from dew point or wind speed from components, use a documented formula and test it. Do not implement speculative scientific conversions.

Use @openmeteo/file-reader as a thin data-access dependency. Research successfully decoded a real CAMS global UV field with version 0.0.20 using OmHttpBackend, LruBlockCache and asCachedReader, then a named child variable. Use that as a tested starting version and inspect its actual exported API; do not copy an outdated README example using a full-download memory backend. Pin the selected version and its WASM dependency. Do not build the app around the entire experimental @openmeteo/weather-map-layer demo. That project is a useful reference for metadata and model grids. Its custom om:// protocol is an application registration mechanism, not a URL the browser can fetch natively.

Observed feasibility evidence from 20 October 2026: one 451x900 UV field decoded to a 405,900-element Float32Array; about 200 KB were transferred across five requests including metadata, HEAD and three 206 range responses, instead of the whole roughly 1.88 MB multi-variable file. Elapsed time in that Node environment was about 0.65 seconds. These observations validate one data sample, not browser, mobile, every layer, or future latency. The WASM binary was about 2.1 MB uncompressed and 195 KB gzipped. Configure and verify compression; do not report compressed transfer if the host actually serves the raw file.

Both the official OM reader and weather-map-layer currently identify themselves as unfinished/experimental and use GPL-2.0 licensing. The default new-project direction is therefore GPL-compatible source distribution with preserved notices. Inspect exact installed licenses, retain license texts and source references, and document corresponding-source obligations for a distributed browser bundle. Do not label the whole dependency graph MIT. Do not change an existing project's license or make its repository public without authorization. If an existing project's license is incompatible, keep the reader experiment isolated and report that specific blocker instead of relabeling the project.

Do not use data-spatial.open-meteo.com as an undocumented unrestricted CDN: the demo's CDN has origin restrictions. Use documented public bucket access. Do not spoof Referer/Origin, use a public CORS proxy, or treat browser access controls as something to bypass.

Initial feasibility work is part of implementation and should precede extensive styling:
1. Fetch and validate the three small metadata files.
2. Initialize the published reader and WASM using the actual package exports.
3. Read one required variable from one completed spatial frame using bounded HTTP ranges. Verify 206 and correct Content-Range, exposed headers, resource length and consistent ETag/version where supplied. Reject unexpected whole-file responses above a safe byte cap instead of allocating them blindly.
4. Repeat with representative wind components, a CAMS global scalar, and one regional pollen field. Exercise at least two variables and two valid times through the browser Worker to a rendered texture; do not validate only a single frozen frame.
5. Record actual compressed bytes, request count, elapsed time, peak decoded allocation estimate, CORS behavior, cancellation behavior, variable units, and no-data representation.
6. Display a real field on a minimal globe and compare several numeric samples to the decoded grid. Confirm orientation at known coordinates.
7. Verify the production Vite build can load its Worker/WASM from a normal HTTP static server and a non-root base path if supported. Prefer a threadless Worker/WASM path. If the actual build requires SharedArrayBuffer/cross-origin isolation, configure and verify the exact COOP/COEP headers on the chosen preview/hosting target and check every cross-origin resource under that policy. Do not assume arbitrary static hosting adds these headers.

Passing a metadata request is not enough. Passing a Node read is not proof of browser, Worker, or deployed-origin compatibility. Treat missing browser validation explicitly.

Most important data performance rule: read only the selected variable and necessary region/frame. Do not download all variables in a multi-variable OM file. Downsampling after downloading does not save bandwidth. Coalesce adjacent range reads and bounded chunk work; do not create one request per output pixel. Bound concurrency, cancellation, and caches. Avoid mixing bytes from different file versions across range responses; invalidate and retry a bounded number of times on a version mismatch. Do not let a single ignored Range header trigger an unlimited full-file download.

Try a globe-resolution overview before detailed fields. Use real low-resolution fields if available, or measured region/chunk reads that genuinely lower transfer. Start with approximately 360x181 or a similarly appropriate display grid for a global overview, but never claim that this output size proves a small download. Increase displayed resolution only when it provides visible value and meets measured budgets. Preserve source resolution separately from rendered resolution.

If the direct reader's browser path is too slow or unreliable, first simplify resolution, ranges, variable selection, and prefetching. Use the pre-approved CAMS WMS path below for CAMS layers when it is more robust. Do not respond by secretly deploying a paid proxy or adding a huge ingest platform.

7. CAMS WMS ADAPTER

Implement a small WMS adapter for UV, PM2.5, and pollen as an allowed alternate spatial route when it reduces transfer or avoids an OM reader problem. Official entry point:

https://eccharts.ecmwf.int/wms/?service=WMS&request=GetCapabilities&version=1.3.0&token=public

Research confirmed public GetCapabilities and small GetMap responses with browser-compatible CORS on the research date. This is not an availability SLA or a statement of unrestricted request volume. Discover current layer IDs, supported projections, dimensions, times, styles, legends, bounding boxes, and query capabilities from GetCapabilities and documentation. Cache metadata and keep request volume modest.

Examples to discover and validate, not blindly assume:
- composition_uvindex
- composition_uvindex_clearsky
- composition_europe_pol_grass_forecast_surface
- composition_europe_pol_birch_forecast_surface
- composition_europe_pol_olive_forecast_surface
- composition_europe_pol_ragw_forecast_surface

Use HTTPS. For WMS 1.3.0 with EPSG:4326, account for latitude/longitude axis order in BBOX; do not swap the globe axes accidentally. For another WMS version or CRS, follow its own axis order. Request a plain georeferenced data image without embedded map foreground, coastlines, text, or a graticule that would be stretched onto the sphere.

Obtain the exact legend/style for the image. A colored WMS PNG is not a numeric field: do not reconstruct exact values from its RGB pixels, apply a different client-side palette, or feed it to a numeric particle simulator. Use supported GetFeatureInfo only if its numerical semantics are confirmed; otherwise a local point forecast remains a separately labeled source. For WMS, legend/image consistency is mandatory even when the provider style differs from the preferred palette.

The inspected composition_pm2p5 default style uses DEFRA DAQI categories. Do not label that default image as PM2.5 concentration in micrograms per cubic metre or as US/European AQI. To satisfy the required PM2.5 concentration map, select a documented concentration style and its exact legend, or keep the numeric OM route. A correctly labeled DEFRA DAQI fallback can be useful, but does not by itself fulfill the concentration-map acceptance criterion.

Inspect actual pixels. A successful status can contain a ServiceException document, an empty tile, an out-of-season zero field, or a transparent outside-coverage region. Validate content type and dimensions and distinguish these cases.

Keep regional pollen within its true extent and mask. Do not stretch a European texture over the world. Respect actual valid times and source run information; do not use the current device clock as a proxy for when the map was produced. Crossfade images only as a short transition; stop at real frames.

Use the public Open-Meteo Weather Forecast, Air Quality, and Geocoding APIs only for requested locations and cached favorites. Research baseline: the hosted free API is noncommercial, with published limits of 600 calls/minute, 5,000/hour, 10,000/day and a pricing-page monthly allowance of 300,000 calls. Limits can apply by both application and IP. A multi-location/multi-variable query is not automatically counted as one billable/rate-limited call. Recheck the current counting rules and stay well below limits.

These are service terms, distinct from the CC BY data license and from the public S3 dataset. The default app has no monetization. Do not imply that changing to commercial use is free merely because the code or dataset is open.

Fetch only variables needed by the panel. Typical weather variables include temperature_2m, apparent_temperature, relative_humidity_2m, precipitation, precipitation_probability, weather_code, cloud_cover, pressure_msl, wind_speed_10m, wind_direction_10m and wind_gusts_10m. Verify exact availability rather than assuming every model supplies every field. Daily values may include temperature extrema, precipitation totals, sunrise/sunset and UV maximum when returned.

Typical air-quality variables include pm2_5, pm10, european_aqi or us_aqi, uv_index, and pollen fields. Pollen species are alder, birch, grass, mugwort, olive, and ragweed where supplied. Do not request an unnecessary full pollutant history for every click.

Default pollen behavior follows documented European coverage and seasonality, not a global promise. A missing value is not zero. For an in-coverage location with genuine zero values, show zero normally. Outside coverage, show unsupported. Within coverage when the provider does not return a seasonal variable, show unavailable/out-of-season only as supported by provider metadata; do not infer the medical absence of pollen.

For a click on an arbitrary coordinate, display coordinates until a reliable place label is available. Do not invent a reverse-geocoding endpoint; a nearby search result is not proof of the actual location's city.

Use approximate coordinates only where adequate; never log or transmit more location information than needed. Explain in Sources/Privacy that coordinates are sent to the selected data provider when the user requests a forecast. Do not request exact location automatically.

9. DATA CONTRACTS AND SEMANTICS

Define typed boundaries, approximately:

LayerDefinition:
  id, localizedLabel, quantity, units, sourceAdapter,
  scalarOrVector, sourceVariableNames,
  paletteId, scaleDomain, temporalSemantics,
  coveragePolicy, supportedQualityLevels.

FieldFrame:
  provider, model, modelRunTime (nullable if not supplied), validTime,
  intervalStart, intervalEnd, timeSemantics,
  sourceGridResolution, displayGridResolution,
  width, height, projection, bounds, rowOrder, longitudeConvention,
  values (TypedArray), optional u/v components,
  validityMask, scaleFactor, addOffset, physicalUnits,
  retrievedAt, sourceReference, provenanceState.

Data states are distinct:
  loading, ready, no-coverage, unavailable, stale-cached, demo.

For raster-image adapters, use a separate RasterFrame contract with georeferencing, style/legend, timestamps and coverage. Do not pretend it contains a numeric values array.

At the adapter boundary normalize units exactly once. Preserve metadata sufficient to explain any transformation. Numbers and colors share the same normalized value definition. Account for K vs C, Pa vs hPa, wind m/s vs km/h, mass concentration units, and model-specific precipitation representation. Open-Meteo OM fields can already be normalized to Celsius, hPa, mm and percent, unlike upstream GRIB fields. The reader can also apply storage scale/offset during decoding. Verify the exact exported variable semantics and decoder behavior before conversion; do not apply GRIB transformations or scale factors twice. Avoid unnecessary decimal precision for coarse forecasts.

Never use falsy checks to classify values: 0 is valid. Treat null, missing, nonfinite values and masks explicitly. Validate physical plausibility without concealing corrupt data through arbitrary clamping.

Precipitation must carry its source interval. If the source stores an amount over a backward interval, an interval-average rate is amount divided by interval duration; label it accordingly. Do not portray that average as minute-scale instantaneous rain. If a source stores cumulative totals from model initialization, derive increments only within the same run with proper reset handling. Do not difference across runs. Some initial frames have no accumulation interval and must remain unavailable. Keep probability, amount and rate separate.

Temperature is 2 m air temperature, wind is 10 m wind, pressure is mean sea level pressure. Apparent temperature is a distinct local metric. Cloud fraction does not encode cloud height or volumetric geometry. UV values must come from a valid product; sunlight angle, temperature, cloud cover or an attractive shader cannot replace UV data.

Pollen concentrations are in grains/m3 for a selected species. Avoid a total concentration that combines species into a fabricated risk category. Any qualitative thresholds must cite the actual species-specific/provider standard. Otherwise show numerical concentration and its trend without medical claims.

10. TIME AND STATE CONSISTENCY

Maintain separate requested-view and displayed-view state. The displayed scientific view is one atomic tuple containing layer, species, provider/model/run, valid time, interval, units, palette/style, coverage and frame. Map, legend, active-layer tooltip and matching chart read that committed tuple together. Never retain an old temperature image under a newly selected pollen legend, even briefly. Mark the requested layer/time as pending until its complete view is ready. Unit changes update displayed data labels and legend together.

Store instants in UTC, using epoch or fully specified ISO timestamps. Format with Intl.DateTimeFormat and an explicit IANA zone. Do not parse a naive local time as UTC. For selected cities use the provider timezone. For arbitrary coordinates without a resolved timezone, explicitly show UTC instead of guessing longitude/15. Globe time can default to UTC; local panel time must name its zone.

Distinguish model run time, forecast valid time, interval, API retrieval time, and cache age. A request fetched now can contain an old forecast. Never relabel cached or recorded data as current.

Build the timeline from real available frames for the active layer/run. When switching layers, retain requested time if available; otherwise visibly state the chosen nearest available time and the adjustment. For the optional wind overlay, require an exact forecast-valid-time match by default. Different provider/model initialization times are allowed only when both sources are identified and their valid times match. If no matching wind frame exists, hide the overlay temporarily and explain why. Nearest-time overlays are outside this release unless a bounded tolerance is explicitly documented and tested; do not choose one silently.

Dragging the timeline immediately moves its handle and updates the requested time. The currently displayed map keeps its own visible valid-time label until the new data arrives. Only the latest request may become active. Keep the previous frame visible with a subtle loading status rather than blanking or freezing the globe.

Playback uses already available/cached frames and bounded prefetch. If the next frame is not ready, pause/buffer with a clear indication; do not advance the time label while the old weather remains on screen. Do not download the entire horizon of every layer on startup.

Use discrete real frames by default. A 150–250 ms crossfade is a transition, not an extra meteorological timestep. During a crossfade between different quantities or provider styles, mark the transition and suppress exact map-value hover readings until the new displayed tuple commits; alternatively use a simple atomic field swap with a UI transition. Numeric temporal interpolation is optional only for quantities whose semantics permit it, with an explicit interpolated state and matched numerical values. Do not interpolate categorical weather codes, AQI categories, missing values, or accumulation totals as instantaneous fields.

A global map sample and a higher-resolution point forecast can disagree legitimately. Label the former as "значение слоя" and the latter as "локальный прогноз" with sources/resolution. Do not silently overwrite one with the other or promise identical numbers across different products.

Pin a consistent run while exploring it where the adapter supports that. Refresh completed-run metadata modestly while visible, and switch to a new run atomically when required frames are ready. Never combine half of an old run with half of a new run without an explicit supported policy. Some WMS products select the latest run for a requested valid time rather than exposing a selectable run; represent run identity as unknown when not returned, use appropriately short caching, and do not claim a pinned-run guarantee for that adapter.

Shared URLs contain requested valid time, not an assurance that an old run remains online. If a saved time has expired beyond retention, explain it and offer the closest currently available time. Do not silently present current weather under the old date.

11. RENDERING AND GEOGRAPHY

Use a moderate-resolution sphere, one data surface and a small number of supporting meshes. Weather cells should not be individual React components or DOM elements. Use TypedArrays, data textures and a palette lookup shader. Change uniforms/textures instead of recreating the scene when changing modes.

Raw numeric textures and masks use an appropriate non-color data interpretation; Earth imagery and palette colors use correct color management. Avoid applying display transfer functions to numeric data. Test known palette values in the actual rendered output, not only in a JavaScript helper.

Normalize lat/lon, document sphere axes, and verify Greenwich, Buenos Aires, Tokyo, the equator, poles and the international date line. Handle grid cell centers vs edges, north-to-south vs south-to-north rows, -180..180 vs 0..360, and the wrap seam explicitly. A regional texture never uses global RepeatWrapping.

Bilinear interpolation must respect masks and geographic coverage. Do not fill holes from distant valid neighbors, interpolate across a regional boundary, or paint an unsupported area with a valid zero. Display no-coverage using a restrained neutral pattern/label distinguishable from the lowest value.

Use native numerical resolution honestly. Smoother shading is a display choice, not a claim of street-level forecast accuracy. Source resolution and rendered resolution should be discoverable in the layer information.

Raycast only when needed, throttle hover inspection, and distinguish drag from click by a sensible movement threshold. Do not select the far side of the planet. Keep touch hit targets and DOM controls outside gesture conflicts. Coastlines and markers should remain legible without visual z-fighting.

Use locally bundled Natural Earth geography or another explicitly licensed equivalent. Prefer a simple original generated land/ocean material over unlicensed Earth artwork. NASA assets require checking the specific asset's credit/rights; do not assume every NASA page asset has the same license. Never use private imagery or a commercial tile service by accident.

12. WIND IMPLEMENTATION

Use actual u/v components and interpolate those components, not angular bearings. Particle movement shows the direction of transport; the conventional wind bearing in the panel describes where the wind comes from. Test easterly/westerly and northerly/southerly synthetic fields.

A GPU update with ping-pong render targets is preferred if robust in the installed WebGL 2 stack. A carefully bounded Worker/CPU simulation with one batched GPU draw is acceptable if measured performance is better and it remains scientifically correct. Do not force complexity solely to say "GPU".

Move particles on the sphere's tangent surface. Account for longitude scale with latitude or integrate in 3D tangent vectors and renormalize. Avoid pole singularities, seam jumps, particles under the globe, and overlong trails after a tab resumes. Clamp frame delta and respawn safely. If simulation speed is exaggerated for readability, disclose it in layer information; do not imply visual transit time is physical travel time.

Start around 8–16k particles on capable desktops and 2–4k on low/mobile quality, then measure and adapt. Use one/few draw calls, shared buffers, and no per-particle React state. Particle count is a budget, not a quality score.

Low quality and reduced motion preserve the scalar speed field, numerical direction, and useful controls. Reduced motion disables continuous trajectories and automatic camera animation. Unsupported float-render-target features must degrade gracefully.

13. PERFORMANCE BUDGETS

These are implementation targets, not claims already measured. Document actual test hardware or virtual renderer, browser, viewport, DPR, network conditions, warm/cold cache, and test scenario.

Interaction:
- Visible response to ordinary controls within 100 ms, independent of data latency.
- Cached layer change begins within 100 ms; transition completes in roughly 250 ms.
- No synchronous field decoding, massive JSON parsing, or React state churn in pointermove/useFrame.
- No stale response can overwrite a newer selection.

Rendering targets:
- Approximately 60 FPS while dragging on a documented normal desktop baseline.
- At least 30 FPS on a documented midrange mobile baseline at adaptive quality.
- Track p50/p95 frame duration after warm-up; report long tasks and visible stalls.
- About 40 or fewer steady-state draw calls as an initial budget, with justified exceptions.
- Start DPR around 1–1.5, cap it; use 2 only when performance allows or the user explicitly chooses it.
- Bound estimated GPU texture/render-target allocation, aiming below 128 MiB, and CPU frame-cache allocation, aiming below 64 MiB. These estimates are not a complete browser GPU memory measurement.

Loading targets:
- UI shell JavaScript around 200 KiB gzip or less.
- Separately lazy-load the 3D engine and data decoder; aim for roughly 450 KiB gzip for the 3D chunk and report the WASM size separately.
- Aim for at most about 2 MiB compressed critical assets and the first displayed field; measure external data transfer separately and disclose any justified deviation.
- The usable HTML shell appears before optional Earth textures and future frames.
- Add performance marks for shell-ready, globe-first-frame, first-real-field, and local-forecast-ready. LCP alone does not prove Canvas readiness.

Core Web Vitals goals are LCP <=2.5 s, INP <=200 ms, CLS <=0.1 at the 75th percentile of real visits. Lab results and a single Lighthouse score do not establish production field performance. Collect only local development measurements by default; do not add a paid analytics service.

Use adaptive quality with hysteresis to avoid oscillation: lower particles, DPR, texture/display grid resolution, and expensive effects in that order as appropriate. Never degrade by substituting fabricated data. Keep manual Auto/High/Low settings usable.

Render on demand when the camera and active scalar layer are still. Continue frames only for active motion/playback/particles, and stop them on hidden tabs or when the scene is not visible. Do not fetch new frames continuously in the background. Pause and reset animation timing on resume.

Reuse materials, geometry, Workers and buffers. Release obsolete textures, targets, listeners and fetches. Verify that allocations stabilize after repeated layer/time changes. Use a bounded LRU and keep only a small active frame window, typically current/previous/next plus a small capped recent cache. Respect Save-Data where available.

If a target cannot be measured because the environment has only SwiftShader/headless software rendering, record that limitation. You can prove functionality there; you cannot honestly claim hardware-mobile FPS. Do not disable 3D in tests merely to obtain a green result.

14. NETWORK, CACHING AND FAILURE BEHAVIOR

Use AbortController and request generations. Bound concurrent remote field requests, initially about 2–4, and cap prefetch to the next one or two frames. Honor Retry-After and exponential backoff with jitter for transient failures; do not retry authorization errors or bad parameters endlessly.

Cache completed immutable model-run frames by source/model/run/variable/valid-time/region/resolution/version. Cache latest metadata separately with a short bounded lifetime; refresh only while relevant. Do not let an old field cache masquerade as a new run. Use modest point-forecast stale times, for example 15–30 minutes depending on product, without unnecessary polling. Revalidate at a meaningful user action or after the cache expires.

An in-browser counter cannot enforce an application-wide API limit. Keep the product explicitly low-traffic and noncommercial, handle 429 honestly, and never rotate proxies/IPs or shard identities to evade quotas. A future broad public launch requires a separate capacity review; do not add that infrastructure now. Request point data only on a committed location selection, never hover/drag; change units locally; reuse already loaded frames. WMS images must not refetch on every animation or camera frame.

Distinguish no-coverage, no-future-frame, temporary outage, offline, invalid data and stale cached data. Each has clear localized text and a useful next action. On failure, retain a valid previous frame with its original timestamp and stale status. Without usable cached data, leave geography visible and show an unavailable layer instead of synthetic weather.

Provide a deterministic opt-in demo/test dataset so the interface and tests can run without network. Mark it clearly in the application as demonstration data and keep its recorded/fixed time. Never silently switch production requests to demo data. Do not bundle an old fixture as the normal "live" first frame.

If a fully offline PWA would expand scope, do not build one. A loaded shell and cached data may remain usable offline; do not promise cold-start offline behavior unless a verified service worker implements it. Favorites/settings storage failure must not crash the app.
